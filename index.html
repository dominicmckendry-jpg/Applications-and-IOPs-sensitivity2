1. Purpose and what changed

This reference helps HPC teams at European universities and research institutes decide where a parallel file system (PFS) pays off, and which one. It answers four questions per application: is it widely used, how sensitive is it to storage IOPS, how would a PFS help, and which PFS fits best in a given setting.

Version 1 listed 100 applications with ratings typed straight into the page and no sources. One "IOPS sensitivity" label mixed metadata and data operations, and the storage tier simply followed from it. Version 2 changes this:

  • 200 applications, each with stated usage evidence and sources.
  • IOPS sensitivity is scored with a written rubric on four measurable dimensions (0–12). Bandwidth demand is scored separately.
  • Every application is assigned one of eight I/O types. The type explains how a PFS helps and drives the PFS comparison.
  • The chosen PFS comes from a transparent, weighted score that you can re-weight for your context.

Disclosure. This page is maintained by ThinkParQ, the company behind BeeGFS. To keep the comparison fair, every performance fit cites a source, the cost and operations scores are labelled as working assumptions, and the weights are adjustable. Several types (shared-file I/O at scale, small-file random reads) favour other file systems under performance-led weights, and the page says so.

Inclusion and exclusion

  • Included: end-user applications and the tools that generate their I/O. That covers workflow engines (Nextflow, Snakemake, AiiDA), software environments (Conda, Jupyter) and container runtimes, because they create the file traffic.
  • Excluded: numerical libraries (HDF5, PETSc, ELPA), compilers, schedulers and storage benchmarks (IOR, mdtest, HPL). Version 1 listed several of these as applications.
  • Balance: national usage data over-represents materials science. In Sweden, for example, biological sciences use 37.9% of national storage but 7.5% of compute. Life sciences, AI and quantum chemistry are therefore included at the depth they occupy on university clusters.

The result is grouped by domain, not ranked. On ARCHER the top 10 codes used about 55% of core hours and the top 20 about 68%, so the long tail matters less for compute but often more for storage.

3. Measuring IOPS sensitivity

Definition. IOPS sensitivity is how strongly an application's time-to-solution depends on the rate of storage operations it can complete: metadata operations and small or random reads and writes. It is separate from bandwidth demand, which is about how many bytes move. A climate model can be low on IOPS and high on bandwidth. A genomics pipeline is usually the reverse.

Each application is scored 0–3 on four dimensions. All four can be measured with Darshan, which most European centres can load as a module, plus server-side counters (BeeGFS server statistics, Lustre jobstats).

DimensionDarshan evidence0123
Metadata intensityPOSIX_F_META_TIME vs read+write time; POSIX_OPENS, POSIX_STATS per second<10% of I/O time10–25%25–50%>50%
Small / random accessPOSIX_SIZE_READ_* and _WRITE_* histograms; POSIX_SEQ_READS ratio<10% of requests under 64 KiB10–40%40–70%>70%, or mostly non-sequential
File count and concurrencyFiles touched per job (darshan-parser --file-list) × concurrent jobs from the scheduler<100 files per job100–10k10k–1M>1M per campaign, or >1,000 concurrent jobs
Scratch dependenceShare of bytes written to files deleted within the job; re-read/rewrite counters<10%10–30%30–50%>50%, or the code needs fast scratch to finish

The total gives the band: Low 0–3, Medium 4–6, High 7–9, Very High 10–12. These thresholds follow the large Darshan study by Luu et al. (HPDC 2015). In that study about 40% of jobs spent more time on metadata than on moving data, and three-quarters of applications never exceeded 1 GB/s.

Bandwidth demand (1–5)

Bandwidth is scored separately: 1 = negligible output; 2 = MB–GB per job; 3 = tens of GB per job or index loads at start; 4 = 100 GB-scale checkpoints or snapshots; 5 = TB-scale output per run, or I/O phases that stall many nodes at once.

High-throughput modifier

Many codes behave very differently when run as ensembles or screening campaigns (VASP high-throughput, GROMACS -multidir, BLAST query farms). Those rows carry an HT flag. In HT use, metadata intensity rises by 1 and file count and concurrency goes to 3.

Status of the numbers in this tool

Rubric scores start from the defaults of the application's I/O type (section 4) and are adjusted where a source documents something specific. applications have I/O behaviour documented in a cited source (basis D); the rest are estimates (basis I). Replace the estimates with measured Darshan values from your own site before relying on them.

5. How a parallel file system helps

A PFS spreads data and metadata across many servers, so performance grows with the number of servers instead of queuing on one NFS head. What that buys depends on the I/O type:

Centres already work around these limits, which shows where the pain is. CSC asks users to package Conda environments into containers because each environment holds tens to hundreds of thousands of files. Sigma2 reports a job taking 47 minutes on local scratch against 20 hours on the parallel file system. Augsburg runs TURBOMOLE scratch on a RAM disk. The RELION developers copy particles to local SSD because their busy shared BeeGFS was slow for that pattern. A PFS on spinning disk alone does not fix random-read workloads; flash for metadata and hot data matters as much as the software.

6. How the PFS is chosen

The tool compares BeeGFS, Lustre, IBM Storage Scale (GPFS) and WEKA in three steps.

Step 1: performance fit per I/O type

Each file system gets a 1–5 fit for each I/O type. The fit assumes each system runs on hardware suited to the type (flash metadata for metadata-heavy work, for instance), so the score reflects design features rather than disk count. Every fit cites the feature it rests on. The full matrix with reasons is on the PFS comparison tab.

Step 2: context criteria

Performance rarely decides a purchase alone. Each file system is also scored 1–5 on cost (licence model and the hardware it needs), operations (admin effort and skills) and flexibility and sovereignty (hardware choice, tiering, vendor jurisdiction). These are working assumptions, labelled as such, and the main place where a reader may reasonably disagree.

Step 3: weighted score

score(PFS, app) = wperf·fit(PFS, I/O type) + wcost·cost(PFS) + wops·ops(PFS) + wflex·flex(PFS)

Four presets set the weights. You can also set your own on the PFS comparison tab.

PresetPerformanceCostOperationsFlexibility
  • Ties: if the top two scores are within 0.15, both are shown as joint choices.
  • Compute-bound apps: for Type H the choice is "No PFS needed", meaning storage is not a buying criterion.
  • Technical best fit: the highest performance fit is always shown next to the weighted choice, so the effect of the context weights is visible.

With the default university weights, BeeGFS comes out ahead for most types, mainly on cost, operations and BeeOND for scratch-heavy work. With performance-only or national-centre weights, WEKA leads small-file and metadata types and Lustre leads shared-file and large-streaming types. Both readings are shown so the trade-off is explicit.

8. Limitations

  • The list is compiled, not ranked; only UK data gives usage shares per application.
  • Most rubric scores are estimates until measured at a site.
  • Fit scores compare design features, not tuned deployments; hardware often dominates.
  • Other systems (DAOS, VAST, Ceph, pNFS/Hammerspace) are out of scope.
  • Feature statements for WEKA come from vendor material and are marked as such.
